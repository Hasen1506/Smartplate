# SmartPlate production readiness audit

**Reviewed:** 27 September 2026. Repository: [Hasen1506/Smartplate](https://github.com/Hasen1506/Smartplate), `main` at `733b69b5e768bfe5ef6bf67f889427bc75f118f2`; public deployment: [smartplate-xgxd.onrender.com](https://smartplate-xgxd.onrender.com/). This combines source, public-documentation and live public-screen review. I did not have Render logs, a Swiggy-approved client, or a live Swiggy account. The reported Swiggy error was: “Render isn't whitelisted for Swiggy connection; this client isn't supported for Swiggy MCP sign in.”

## Verdict

SmartPlate is a capable **Chennai trial**: a working planner, installable web app, private profile keys, a simulator, and a solid automated test baseline. It is **not ready for real commerce or durable personal data**. The most important distinction is that a green simulator test does not validate Swiggy OAuth, live menus, item identity, allergy safety, cart semantics, checkout, or payment. The app itself says that the live connection has not been tested against Swiggy.

**Required product direction:** the user's selected Swiggy delivery address must drive restaurant discovery; users should star provider restaurant IDs, browse the current menu, select exact provider item IDs, review the real cart total and payment choice, explicitly place the order, and track it. A seeded dish list cannot be the ordering catalogue. The PR now implements this connected path separately from the sample planner and includes a gated Cash on Delivery placement flow. It still needs Swiggy approval, staging contract validation, durable storage and deployment before anyone can actually complete that path. UPI needs a separate pending-payment, payment-status and `confirm_order` flow; a UPI initiation must never be shown as a placed order. [Swiggy's end-to-end Food recipe](https://mcp.swiggy.com/builders/docs/build/recipes/order-food/) and [place-order reference](https://mcp.swiggy.com/builders/docs/reference/food/place_food_order/) describe those requirements.

The new profile setup in the PR no longer asks users to choose from sample restaurants or adopts a budget computed from them. It takes their own budget, then opens the Swiggy connection step. Once connected and an address is selected, Today and Places lead with provider search and menus. The weekly optimizer remains a **demo** because its candidates, nutrient values, availability and prices still come from the seeded catalogue. Moving the optimizer onto verified live menu candidates is separate follow-up work; do not treat its plan as a purchasable basket.

The immediate connection blocker is **provider approval**. Swiggy's published [authentication](https://mcp.swiggy.com/builders/docs/start/authenticate/) and [access](https://mcp.swiggy.com/builders/docs/operate/access/) instructions require an exact-match allowlisted HTTPS redirect and production onboarding. Dynamic client registration is part of OAuth; it does not by itself approve a new hosted client. The reported message is consistent with Swiggy rejecting the Render callback/client. The public docs do not state a blanket ban on Render. The callback computed by this app for the supplied deployment URL is **`https://smartplate-xgxd.onrender.com/swiggy/callback`**. Ask Swiggy to approve that exact URI; if the domain is ineligible, ask whether an owned HTTPS domain can be allowlisted. A different host alone will not establish access.

**Request to send through Swiggy Builders Club:** “We are building SmartPlate, a user-confirmed Food ordering app at `https://smartplate-xgxd.onrender.com/`. Please approve the exact OAuth redirect `https://smartplate-xgxd.onrender.com/swiggy/callback` for staging and explain the production approval process. We need Food MCP access for saved addresses, address-scoped restaurant and menu search, cart, payment options, user-confirmed Cash on Delivery placement, order history and tracking. Is an `onrender.com` subdomain eligible for allowlisting? If an owned domain is required, please confirm that requirement and any client-registration or test-account steps. We will not enable real placement until the staging flow, retry recovery and support procedure pass.” This is a prepared request, not a message sent to Swiggy.

## Live Render walkthrough

The public site loaded and the sample profile, Today screen and **More → Swiggy connection** screen rendered. This tests the deployed public experience, not the proposed PR: the PR has not been merged or deployed. The connection screen said “Not connected” and “Connect Swiggy,” but did not display the required callback URL or explain provider allowlisting. It described a fixed “14 tools,” while the current official Food tool reference lists more; capability text should come from authenticated discovery or stay general. I did not start an OAuth session, so the exact provider error remains the user's reported observation.

I expanded the sample profiles and chose **Arjun**. His profile had no recorded allergies, yet the banner claimed the sample had fictional allergies. His next breakfast was **Peanut Chikki Sweet** at Adyar Ananda Bhavan for an estimated ₹94. A sweet can be a snack or dessert, but it is a poor default for a complete breakfast. The PR now labels sample data accurately and excludes marked desserts from meal planning, shortlists and manual meal replacement. Existing seeded databases are covered by name and cuisine checks; after deployment, verify migrated and user-added catalogue records too. The screen also showed a skipped lunch and a cook-at-home dinner, which reinforces the need to explain skips and nutrition trade-offs prominently.

I could not independently verify private profiles, a completed Swiggy sign-in, live item/cart behavior, purchase flows, or Render persistence from the public walkthrough. One Places navigation attempt did not complete in this browser environment, and a direct API probe was blocked by the browser client; treat that as a retest item, not a confirmed app defect.

## Changes prepared in draft PR #17

The [draft PR](https://github.com/Hasen1506/Smartplate/pull/17) shows the exact callback URL in Settings and corrects misleading sign-in and planning copy. For connected users, Today and Places now use the selected Swiggy address to search real restaurants, save favorites by provider ID, show fresh provider menus, review an exact item, and confirm a cart update. The seeded weekly planner is marked as a separate demo. The cart path rejects uncertain stock, customizations and profiles whose ingredient rules cannot be verified, then reads the cart back. A separately gated Cash on Delivery path refreshes the cart total and payment availability, displays the full address, requires explicit confirmation, records a single nonrepeatable placement attempt and exposes tracking. The PR also rejects `success: false` provider replies, stops guessing ambiguous price units, and keeps sample desserts out of meal slots. These changes are **proposed, not deployed or validated against Swiggy staging**. The findings below describe the reviewed `main` version; the PR cannot clear provider approval, live contract, durable storage, UPI or wider purchase lifecycle gates.

## P0: fix before any real-user production launch

1. **Get Swiggy access and prove the contract.** Show the exact callback URL in Settings, apply through [Builders Club](https://mcp.swiggy.com/builders/docs/operate/access/), obtain staging access, run OAuth on the deployed origin, record the authenticated `tools/list` schemas, and verify `get_addresses`, restaurant search, menu, cart and 401/429 behavior. Swiggy's [go-live checklist](https://mcp.swiggy.com/builders/docs/build/ship-to-production/) calls for an allowlisted redirect, approved production access, and a green staging period. A local fake cannot clear that gate. The current [vendor note](https://github.com/Hasen1506/Smartplate/blob/main/docs/vendor/swiggy/README.md) acknowledges the gap.
2. **Make data durable before accepting personal profiles.** [render.yaml](https://github.com/Hasen1506/Smartplate/blob/main/render.yaml) chooses a Free web service and the default SQLite database lives on its ephemeral filesystem. Render says that filesystem changes, including SQLite, are lost on **spin-down**, restart and redeploy; Free services spin down after 15 minutes idle ([Render Free](https://render.com/docs/free)). A paid single-instance web service with a disk and `SMARTPLATE_DB=/data/smartplate.db` is the quickest private pilot. Add tested backups and restores. For multi-instance production, migrate to Postgres and a migration tool; a Render [persistent disk](https://render.com/docs/disks) is limited to one instance and changes deployment behavior. Keep `SMARTPLATE_SECRET` and VAPID key stable and outside the database.
3. **Stop treating sample dishes as verified live items.** [`fill_cart`](https://github.com/Hasen1506/Smartplate/blob/main/smartplate/integrations/swiggy_live.py#L321) takes a sample planned dish, uses a cached browse menu, picks a fuzzy name match at 0.55, then mutates the cart. It does not validate exact item identity, stock, required variants/add-ons, or allergy/medical rules. Swiggy says [`get_restaurant_menu`](https://mcp.swiggy.com/builders/docs/reference/food/get_restaurant_menu/) is a compact browse view and [`search_menu`](https://mcp.swiggy.com/builders/docs/reference/food/search_menu/) provides full customizations; the user should review the item before cart mutation. Replace this with a fresh, restaurant-scoped `search_menu` result, display exact item, restaurant, address, variants, availability and quote, then require explicit confirmation. If any rule cannot be verified, fail closed and hand off to Swiggy for human review.
4. **Correct safety and budget promises.** The welcome screen currently promises allergies and budget are hard limits ([frontend](https://github.com/Hasen1506/Smartplate/blob/main/smartplate/static/app.js#L249)); that is true only of the seeded candidate set and estimated cost. Live Swiggy menus do not expose enough allergen detail to establish cross-contact safety, and [`menu_for`](https://github.com/Hasen1506/Smartplate/blob/main/smartplate/integrations/swiggy_live.py#L299) only hides marked non-veg items in the display. The cart path does not apply those checks. Present the plan as an estimate; require user verification for ingredients, dietary status and final payable total. Do not call a projected budget a guaranteed spend ceiling until actual charges and refunds are reconciled.
5. **Give the app a real purchase lifecycle before considering placement.** Current orders and receipts mix simulated and self-reported events. Build `planned → quoted → cart prepared → user approved → submitted → accepted → delivered → charged/refunded → eaten`, each with provider IDs, timestamps, amounts and source. Swiggy says [`place_food_order` is not safe to blind-retry](https://mcp.swiggy.com/builders/docs/build/ship-to-production/); after an ambiguous failure, inspect order history/status before retrying. Keep real placement disabled until approval, exact consent, reconciliation and support ownership exist.
6. **Make reminders reliable or label them best effort.** The [push worker](https://github.com/Hasen1506/Smartplate/blob/main/smartplate/push.py#L147) only runs inside an awake web process and drops reminders over 20 minutes late. Render Free explicitly sleeps ([Render Free](https://render.com/docs/free)). For production, use an always-on service and durable job store/worker, plus end-to-end delivery checks. Calendar export can remain an alternative, but importing an `.ics` file is not two-way calendar sync.

## Walkthrough changes that would make the app feel credible

1. **Entry:** Ask location and address before showing restaurants. Today [`CITY = "Chennai"`](https://github.com/Hasen1506/Smartplate/blob/main/smartplate/everyday.py#L20) is fixed for every new profile. Show a clear Chennai trial gate; do not imply all-India serviceability.
2. **Setup:** Start with meals, budget and hard exclusions. Let usual places and nutrition goals be refined after the first plan. Label the budget as a planning estimate and show how many meals were skipped to fit it.
3. **Today:** One primary action based on actual capability: “Open Swiggy search” for unconnected users, “Review matched live item” only after approved connection and fresh match. Do not show a cart action when variants, safety or serviceability cannot be verified.
4. **After hand-off:** Ask “Ordered?”, “Delivered?”, “Ate it?” separately. Capture actual paid amount and restaurant/item changes before claiming spend or nutrition adherence.
5. **More:** Keep account, address, reminders and data controls prominent. Put the 17-feature catalogue, community experiment and auto-order simulator under a clearly marked demo/experiments section. “Adopt” currently just counts interest rather than applying a template ([community](https://github.com/Hasen1506/Smartplate/blob/main/smartplate/domain/community.py#L48)); label it accordingly.
6. **Failure states:** A rejected OAuth redirect should show “Swiggy has not approved this callback/client,” the exact callback URL, a link to onboarding and continued manual hand-off. A lost Render database should tell the user the profile is gone, not just ask them to sign in again.

## Recommended release sequence

**Stage A — honest public demo.** Keep free Render only for disposable sample profiles. Hide or clearly gate the unverified live cart. Show the exact callback and external approval requirement. Remove universal safety/price guarantees. Keep simulated ordering visibly separate. Success: a first-time visitor can tell exactly which data and actions are simulated.

**Stage B — private durable pilot.** Paid always-on Render instance with a mounted disk, stable secrets, backup/restore drill, single instance, 10–20 invited users, no unattended orders. Swiggy staging approval and an end-to-end recorded test of sign-in, addresses, search, item details, cart, Cash on Delivery availability, real placement, order history/tracking, 401/429 and logout. Enable `SMARTPLATE_LIVE_ORDERS=on` only after these checks and approval. Success: profiles and the nonrepeatable order-attempt record survive redeploy, reminders arrive at the intended time, and no wrong item or rule violation reaches an order.

**Stage C — public Food ordering product.** Provider-approved production access, fresh verified item and quote, explicit user confirmation, actual spend reconciliation, data export/deletion, incident/runbook ownership, observability and load testing. Add UPI only with payment-status polling and confirmation; support customizations, multiple dishes and other payment methods only after the provider contract is validated. Success: a user can choose a real restaurant and item, see the full delivery address and payable total, place and track an approved order, and reconcile it without presenting estimates as facts.

**Stage D — optional autonomy.** Only if Swiggy's agreement expressly permits it: user-authored per-order/day/week caps, exact merchant/address/item limits, quiet hours, revocation, anomaly stop, non-idempotent order recovery, support/refunds and a monitored kill switch. Do not equate `mcp:tools` OAuth scope with business permission to place unattended orders.

## Expansion opportunities after the core loop works

| Vertical | Narrow first experiment | Dependency / reason to wait |
|---|---|---|
| Groceries and pantry | “Cook tonight” basket from verified pantry deficits; track expiry and actual waste. | Official Instamart access, inventory input that users maintain, fresh stock and price. |
| Households | Shared weekly cap, per-person exclusions and fair preference rotation. | Real member accounts/consent; current [cost splitting](https://github.com/Hasen1506/Smartplate/blob/main/smartplate/domain/household.py#L39) is a placeholder. |
| Work and shift meals | Employer meal allowance with policy rules and simple reconciliation. | B2B consent, admin controls, payment/expense integration and support. |
| Nutrition | Source-labelled confidence bands and dietitian-reviewed rules for selected cohorts. | Real ingredient/nutrition source, portion data, clinical review for medical claims. |
| Restaurants and dining out | “Delivery vs dine-out” decision from true travel/time/price, then a user-confirmed reservation. | Dineout approval and separate cancellation/support flows. |
| Travel and events | Meal plan adapts to temporary location, calendar and event timing. | Location consent, current serviceability, explicit address changes. |
| Financial planning | Food spending forecast and verified month-end variance, without credit/loan features. | Actual transaction reconciliation and user trust; avoid invented savings. |

**Product priority:** prove that SmartPlate saves decisions and keeps an honest food budget for one repeat cohort before broadening to 17 feature surfaces. Track first valid plan, week-one acceptance, hand-off-to-ordered conversion, actual-versus-planned spend, wrong-item/safety incidents, reminder delivery, week-four retention, and support minutes per user.
